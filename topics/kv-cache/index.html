KV Cache 三条路线

「长上下文太贵，三家的解法完全不同」

一条走向「让 KV 变成常数」，一条走向「把 KV 压到极致」，还有一条两者都做。

三家的答案

Kimi K3
概览页 →

3:1 的线性/全注意力配比 —— 只有 1/4 的层需要存 KV，KV Cache 最多削减 75%。

Qwen3.8-2.4T-A95B
概览页 →

同样的 3:1 配比，但线性层用 Gated DeltaNet 实现，状态大小与头数配置不同（128V/16QK）。

DeepSeek V4.1 Flash
概览页 →

CSA2 + FP4 主 KV —— 不减少要存的层，而是把每个 token 压到 890 字节，持久 KV 约 1/8。

分解看 · K3 的 93.8% 是怎么省出来的（单位：MB / token）
基线：93 层全用 MHA2.67 MB
换成 MLA（每层 latent 3584）0.67 MB
3:1 配比（只留 23 层存 KV）0.16 MB
两级各砍约 75%，乘起来只剩 6.2%。注意「3:1 配比」这一级是本站反复出现的那条杠杆 —— n 层线性配 1 层全注意力，KV Cache 恰好削减 n/(n+1)。

同样是「让长上下文跑得动」，K3 与 Qwen3.8 动的是层数， V4.1 Flash 动的是每层的存储精度 —— 后者一步跨了两个数量级。 以 1M 上下文粗略估算：K3 约 173 GB、Qwen3.8 约 49 GB、 V4.1 Flash 约 956 MB，而 93 层全 MHA 的基线要 2796 GB。 这也解释了为什么 V4.1 Flash 一侧更强调「跨层共享主 KV」：一旦每 token 已经压到几百字节， 决定成败的就变成「这份 KV 有没有被重复存了 20 遍」。

估算口径：MHA 基线 = 4 × hidden 字节 / 层 / token（K、V 各 hidden 维 BF16）； K3 = 2 × latent 3584 字节 / MLA 层 × 23 层（忽略 RoPE 部分）； Qwen3.8 = 4 个 KV 头 × head_dim 128 × 2(K,V) × 2 字节 × 23 层； V4.1 Flash 用官方口径 890 字节 / token。真实部署还要乘上 batch、页式管理与框架 padding。
